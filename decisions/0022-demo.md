# 0022 -- animated policy-visualization demo (D22)

## Context

After all seven members (LiteLru, Sieve, S3Fifo, WTinyLfu, Slru, TwoQ, Arc) and
`dump()` / `restore()` (S14, D21) exist, DEBATE item 16 asks for the moat's third
pillar (the shipped measurement tool, DEBATE item 10) made VISIBLE: ONE shared
trace fed to all seven members side by side, each drawn with its OWN mechanics as
ops stream, with a running "% of Belady optimal" readout per member. The "one
interface, different policy" thesis SEEN, not just read.

## D22.1 -- dump() IS the visualization model

The demo renders each member STRICTLY from the object `dump()` returns after each
op. There is NO shadow re-implementation of any member's mechanics in the demo.
The snapshot is the same serial form `restore()` consumes, so what is on screen is
literally the cache's own state: the Sieve hand + visited bits, the S3Fifo / TwoQ
ghost rings, the WTinyLfu Count-Min sketch, the Arc `p` and `_seg`-tagged lists,
and the `_exp` column when ttl is on. If the demo ever needs member state that
`dump()` does not expose, that is a `dump()` gap to fix in a member session --
never a demo-side computation. This is WHY S13 follows S14.

The falsifiable form (Demo.test.mjs): for each member over >= 2000 ops, the
renderer's input model deep-equals `dump()` -- zero shadow fields, every member's
snapshot shape covered. A renderer that dropped a field (e.g. the Sieve hand) or
invented one would fail the deep-equal.

## D22.2 -- REJECTED alternative: a demo-only introspection hook on Lru.js

Considered: add a small demo-only accessor (e.g. `_viewState()`) to each member so
the demo could read internals directly. REJECTED. It pollutes the shipped surface
with a method that exists only for a dev artifact, and -- worse -- it can DRIFT
from real state (a second code path that computes what the demo shows), which is
exactly the "can the picture lie?" failure this session must prevent. `dump()` is
the single honest source: it already exists, it is exercised by restore(), and it
cannot silently diverge from the cache. Zero new introspection surface on Lru.js.

## D22.3 -- never shipped; zero shipped-surface change

The demo lives in `demo/` and is NEVER in the npm tarball -- it is absent from
`package.json` `files[]`, and the /release pack gate already asserts `demo/`
absent. `Lru.js`, `Lru.d.ts` and `benchmark/Bench.mjs` are CONSUMED, never edited
(`git diff --stat` on all three MUST be empty at the end of S13). Zero runtime
deps hold for what ships; the demo is a dev artifact. The only prose that lands is
a README "Watch the policies" section, one `llms.txt` pointer, and `demo` /
`demo:serve` entries in `package.json` `scripts` (scripts only -- NOT `files[]`,
NOT any version site; VERSION moves only at /release 1.9.0).

## D22.4 -- MEDIUM: browser page + zero-dep Node server (the node:url split)

An animated browser page (`demo/visuals.html` + ES-module engine/renderers,
canvas + requestAnimationFrame) matching the lite-binary-reader house pattern
(a runnable `.mjs` entry + a `.html` visual page; `npm run demo` -> node).

The browser page imports ONLY `../Lru.js`. It does NOT import
`benchmark/Bench.mjs`, because Bench.mjs statically imports `node:url` (for its
direct-run guard, ~line 462) -- a Node builtin the browser cannot resolve. That
constraint FORCES a split:

  - `demo/serve.mjs` -- a zero-dep Node http server. It imports Bench.mjs
    (`zipfTrace` / `loopTrace` / `scanTrace` / `makePrng` + `beladyOpt`),
    computes the trace + Belady OPT SERVER-SIDE, and serves it to the page as
    JSON (`GET /trace.json?kind=zipf&seed=1&cap=32`). It also serves the repo's
    static files so the page's `../Lru.js` import resolves.
  - `demo/Visualize.mjs` -- the headless engine. Imports ONLY `../Lru.js`, so it
    loads in the browser. Its Node-main block (`npm run demo`) DYNAMICALLY imports
    Bench.mjs + `node:url`, guarded by `typeof process !== 'undefined'`, so that
    path never executes in the browser.

The demo consumes Bench.mjs; it never edits it.

## D22.5 -- occupancy only; capacities / geometry omitted from dump() (owner ruling)

`dump()` captures OCCUPANCY -- which slots are in which list, visited bits, the
hand position, ghost keys, Arc `p`, and the sketch COUNTER VALUES that are in the
snapshot -- but NOT fixed geometry: segment / ghost / window capacities and the
sketch's row-count / width are construction-time constants absent from the
snapshot. The demo therefore draws occupancy only. It does NOT reconstruct
capacities or geometry from anything else -- doing so would be shadow mechanics.
This is an accepted limitation for S13, recorded here as an owner ruling: widening
`dump()` to carry geometry is a separate member-session decision, not a demo
workaround.
