# 0013 -- S3Fifo: the SMALL/MAIN split, the ghost, and the capacity-1 edge, D13

Status: accepted (S5 -- the admission-controlled family member)

## Context

S5 adds S3-FIFO (Yang et al., SOSP'23 -- "FIFO queues are all you need for cache
eviction"), the 1-bit visited variant, as the third member of the family beyond
the classic-LRU reference (`LiteLru`) and the SIEVE headline (`Sieve`). S3-FIFO is
quick-demotion + lazy-promotion over THREE FIFO structures:

  - a SMALL (probation) FIFO and a MAIN FIFO, both threaded intrusively through the
    SAME shared `_next`/`_prev` columns (two separate rings, each with its own
    head/tail). `_next` toward the tail (older), `_prev` toward the head (newer).
    A slot is in exactly ONE ring (or free) at a time.
  - one VISITED bit per entry (the Uint8Array-over-bitpack ruling of D12 stands: a
    hit is a single unconditional byte store, no mask/shift).
  - a GHOST queue of recently-evicted keys: bounded, FIFO, keys-only.

`get`/`put(update)` set the visited bit and MOVE NOTHING (0 relinks -- the headline
S3-FIFO shares with SIEVE). New keys enter SMALL (probation) unvisited, unless the
key is currently in GHOST -- a second sighting of a recently-evicted key -- in which
case it is admitted straight to MAIN and consumed from the ghost. At capacity one
eviction step runs: if SMALL is at/over its target it takes the SMALL tail (a proven
= visited entry GRADUATES to MAIN, an unproven one is evicted and its key recorded in
ghost); otherwise it takes the MAIN tail (a visited entry gets one second chance, an
unvisited one is evicted -- MAIN evictions are NOT ghosted). The result is scan
resistance: a flood of distinct one-hit-wonders enters SMALL unvisited and sweeps
straight back out without displacing the proven-hot set in MAIN.

`S3Fifo` ships as a THIRD named export in the existing `Lru.js`, NOT a new file (the
same file-shape ruling as `Sieve`: single PascalCase main file + `sideEffects:false`
+ named exports already deliver the tree-shake moat). It rides the SAME `SlotStore`
substrate (decisions/0011) via the shared `newStore` factory: default Map backing,
opt-in `keys:'int'` strict-zero backing, the same `[lite-lru]`-tagged int-key door,
the shared conservation invariant, and the onEvict fire-after + `_inOnEvict`
reentrancy guard (decisions/0002). No change to `package.json` `files[]` or `exports`.

## The decision -- D13

### Split rounding (frozen in the constructor)

```
smallCap = Math.max(1, Math.floor(capacity / 10));
mainCap  = capacity - smallCap;
ghostCap = mainCap;
```

The 10% probation split is the paper's recommendation. `Math.max(1, ...)` keeps SMALL
non-empty for small capacities (floor(9/10) = 0 would otherwise disable probation),
so admission always routes through SMALL first. SMALL has no admission ceiling: its
`smallCap` is a target the EVICTION sweep enforces (`_sSize >= smallCap` selects the
SMALL tail), never an insert-time cap -- so a burst of inserts can leave SMALL well
over `smallCap` until evictions drain it, exactly as the algorithm intends. A visited
SMALL tail graduating to MAIN may transiently push MAIN over `mainCap`; the outer
loop (a subsequent MAIN eviction step) reclaims it. This transient overshoot is by
design and is invisible to `validate()` (which runs between ops, never mid-sweep).

### The capacity-1 edge (mainCap == 0, ghostCap == 0)

At capacity 1: `smallCap = 1`, `mainCap = 0`, `ghostCap = 0`. With no ghost, every
newcomer enters SMALL. With `mainCap == 0`, a visited single entry GRADUATES into a
zero-capacity MAIN and is then evicted from MAIN within the SAME eviction step (its
visited bit was cleared on graduation, so the immediately-following MAIN step finds it
unvisited). So a capacity-1 cache degenerates to a 1-bit second-chance FIFO over a
single slot: it can never retain more than one key, and a visited entry is evicted on
the next insert just the same. The implementation and the brute oracle agree on this
edge exactly, and `validate()` / conservation stay exact through it (the transient
MAIN overshoot to size 1 is mid-sweep, never observed between ops). This is the ONLY
special case; no `mainCap == 0` branch is needed in the hot path -- the general sweep
handles it because graduation-to-empty-MAIN followed by a MAIN eviction is a valid
two-step of the same loop.

### Ghost representation (mirrors the D3/D11 Map-vs-int asymmetry)

  - `keys:'int'` -> STRICT zero-alloc: a fixed open-addressed Int32 membership table
    (state byte + backward-shift deletion, no tombstones -- the same shape as
    `IntSlotStore`) PLUS a power-of-two Int32 FIFO ring (masked indices). Both sized
    once at construction, never grown. Membership test, insert, and bounded-eviction
    (evict-oldest when full) are all O(1) and allocate NOTHING -- proven by t6 Gate
    S3FIFO, which churns strictly-increasing int keys so the ghost writes on every op
    and the ring/table buffers must not grow.
  - default Map backing -> a `Set` (a key->nothing membership set) PLUS an `Array`
    FIFO ring. Honestly AMORTIZED: a `Set` resize can allocate -- the SAME caveat D3
    already states for the Map keyed index, restated here for the ghost. It retains up
    to `ghostCap` recently-evicted KEYS.

BOUNDED KEY-RETENTION (retention hygiene): the ghost retains up to `ghostCap` KEYS,
NEVER values. Values are dropped the instant an entry leaves a slot (SlotStore
`freeSlot`/reuse already null the payload columns); the ghost never touches `_vals`.
A ghost slot's key ref is dropped when it ages out of the ring (the default-backing
array slot is set to `undefined`, the int ring holds primitive int32s). t7's WeakRef
census proves evicted VALUE objects are collectible even while their KEYS still sit in
the ghost -- a ghost that pinned values would be a leak the tracker size() cannot see.

Ghost consumption (a key re-admitted to MAIN is removed from the ghost) is O(ghostLen)
via an in-place ring shift, but is COLD: it fires only when admitting a key that was
in ghost, never on the sequential-key hot path, and it allocates nothing.

### Uniform surface + policy law unchanged

`S3Fifo` implements the SAME `LiteCache<K,V>` surface as `LiteLru`/`Sieve`
(get/put/has/peek/delete/clear + size/capacity), so `new LiteLru(n)` swaps for
`new S3Fifo(n)` and stays type-checked -- the admission-control policy is INTERNAL,
never in the surface. `has`/`peek` are visited-neutral and never touch the ghost.
The onEvict reentrancy contract (decisions/0002) and the D7 undefined-value contract
hold unchanged. The `victim()` differential twin (`_peekVictim`) is TEST-ONLY (never
a hot path), so it replays the exact `_evict` sweep on CLONES of the four mutable
columns + ring endpoints -- guaranteeing it can never drift from the real eviction.

## Consequences

  - The S3-FIFO hit path relinks NOTHING (0 `_next`/`_prev` stores in EITHER ring)
    and sets exactly ONE `_vis` byte -- strictly cheaper than classic LRU's
    interior/tail relink (5/4), pinned by `CountedS3Fifo` in t6 Gate S3FIFO.
  - Two byte columns per slot are added at fixed capacity: `_vis` (visited) and `_q`
    (which ring a slot is in, so `_detach` fixes the correct head/tail). Both
    allocated once, never grown; their `byteLength` is unchanged start-to-finish under
    churn (t6 Gate S3FIFO checks `_vis`/`_q`/`_next`/`_prev`/the int index/the ghost
    buffers all hold).
  - `delete`/`clear` zero `_vis` on free/reset and empty both rings + the ghost.
  - Scan resistance is a NAMED, gated law: t0 S2 and t2 H prove a proven-hot key/set
    survives an unbounded one-hit-wonder flood (with a non-vacuity check that the cold
    keys really are evicted). t9 C8 (a get that graduates-on-touch instead of at
    eviction) proves the differential/law gate REJECTS a policy that breaks deferred
    promotion.
  - The public API is additive; VERSION stays "1.0.0" (moves only at /release).
