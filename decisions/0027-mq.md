# 0027 -- Mq: the twelfth member, Multi-Queue (m=8), D27

Status: accepted (S20 -- the frequency-band-with-logical-decay member; an honest, byte-countable
per-access cost with a PROVEN non-exceedable link ceiling, NOT a false constant)

## Context

S20 adds `Mq` as the twelfth `LiteCache<K,V>` family member: Multi-Queue (Zhou, Philbin & Li,
USENIX ATC'01). MQ ranks a block by a FREQUENCY BAND (the highest set bit of its reference count)
across m LRU queues, and DECAYS idle blocks over a LOGICAL clock: a block untouched for `lifeTime`
ticks is demoted one band toward Q0, so a once-hot block that goes cold becomes evictable again.
Eviction takes the LRU tail of the lowest non-empty queue. It is the recency+frequency hybrid the
literature pairs with LRU-2 and 2Q; unlike `Lfu` (exact frequency, no decay) it forgets, and unlike
`Slru`/`TwoQ` (2 segments) it grades frequency across 8 bands.

It rides the SAME `SlotStore` substrate (decisions/0011) via the shared `newStore` factory:
default Map backing, opt-in `keys:'int'` strict-zero backing, the `[lite-lru]`-tagged int-key door,
the conservation invariant, the onEvict fire-after + `_inOnEvict` reentrancy guard (decisions/0002),
TTL (decisions/0017 -- the WALL-CLOCK ttl, distinct from the logical clock), zero-GC iteration
(decisions/0018), opt-in stats (decisions/0019) and snapshot/restore (decisions/0021). No new file;
`Mq` is a named export in `Lru.js`.

## The decision -- D27

### D27.1 -- m is fixed at 8 (no knob)

The queue count m is fixed at 8 (Q0..Q7). With `band = min(floor(log2(rc)), 7)`, eight bands cover
reference counts 1..127 exactly (Q0 = rc 1, Q6 = rc 64..127) and saturate everything >= 128 into Q7
(D27.3). Eight bands is the value the paper studies and is enough to grade any realistic hot set;
a knob would fork the hot path (a variable band index and a variable-length aging sweep) against
the fixed, byte-countable hot body this suite headlines. Deliberate deviation from the paper's
general-m formulation; it does not change MQ's eviction behavior for the studied m=8 setting.

### D27.2 -- a LOGICAL clock and lifeTime = capacity (SEPARATE from the wall-clock ttl)

Aging runs on a monotone LOGICAL clock `_t` (a plain number field, Float64 semantics, exact to
2^53), bumped `++_t` on every reference. Each reference stamps the accessed block's expire time
`_exq = _t + lifeTime`, and `lifeTime = capacity`. This logical clock is EMPHATICALLY DISTINCT from
the optional wall-clock `ttl`/`clock` (decisions/0017), which stays a pure staleness gate: the two
never interact. lifeTime = capacity ties the decay horizon to the cache size (a block survives about
one full turnover of references before it can decay a band), which is the standard MQ default and
needs no separate knob.

### D27.3 -- band saturation is a FAIL-CLOSED clz32 guard (the RISK)

`band(rc) = rc >= 128 ? 7 : (31 - Math.clz32(rc))`. The `rc >= 128` short-circuit is not an
optimization -- it is a CORRECTNESS guard. `Math.clz32` coerces its argument mod 2^32, so a refcount
past 2^32 would wrap to a small (or zero) value and `31 - clz32(...)` could produce a band > 7 (e.g.
rc = 256 -> 8) or even negative (rc = 2^32 -> -1), indexing `_qn`/`_qHead`/`_qTail` OUT OF RANGE.
Short-circuiting every rc >= 2^7 to the top band Q7 keeps `Math.clz32` consulted only over its safe
1..127 domain, so the band is ALWAYS a valid 0..7 index. Tested directly (t0 MQ5, t6 Gate MQ): a key
driven past 128 references lands in Q7 and stays coherent under validate(). "null is not zero", and a
wrapped band is not a valid band.

### D27.4 -- the victim rule: LRU tail of the lowest non-empty queue

Resident blocks live in 8 disjoint intrusive LRU queues over the SHARED `_next`/`_prev` columns (a
slot is in exactly one), with `_qHead[q]` = MRU and `_qTail[q]` = LRU per band. Eviction scans Q0,
Q1, ... for the first non-empty queue and evicts its tail. Because a block is placed by its
frequency band and decays toward Q0 when idle, this evicts the least-valuable block: a rarely-used
Q0 block before a hot high-band one, but a once-hot block that has decayed to Q0 is fair game. The
scan is at most m = 8 queue-head reads (a constant), so eviction is O(1).

### D27.5 -- bounded keys-only + refcount Qout history, refcount-preserving re-admit

The paper's Qout retains descriptors (including the refcount) of recently-evicted blocks so a
returning block resumes at its remembered frequency. This member keeps a BOUNDED history
(`MqHistory extends ArcGhost`, cap = capacity, drop-oldest) with a PARALLEL fixed-size Float64
refcount ring aligned to the key ring -- the same ring pattern as Lirs/ClockPro/LruK, extended with
one aligned numeric column, NEVER a per-key array. Every eviction records the victim key + its
refcount; a put of a key still in Qout re-admits it at `rc = savedRc + 1` (the put is a reference),
so an evicted rc-5 block re-enters at band(6) = Q2 (proven in t0 MQ4, Mq.test.js). delete/reap are
NOT recorded (a removal keeps no metadata, like the rest of the family).

OWNER-RULING DEVIATION. This is a bounded approximation of the paper's Qout: (1) it is bounded to
cap and drop-oldest, so a block evicted long ago is forgotten; (2) it stores only the refcount, not
the full timing history. This trades some fidelity for a strict memory bound and zero per-key
allocation, matching Lirs D23 / ClockPro D25.2 / LruK D26.4. It changes the re-admission STAMP, not
the resident-set victim RULE; the differential oracle checks the whole observable behavior exactly.

### D27.6 -- the per-access cost: HONEST, and a PROVEN non-exceedable link ceiling

This is the crux, and the lesson of the rejected ClockPro-S18 false-bound attempt. MQ's hit is
NOT a 0-link-write lazy-promotion hit (unlike Sieve/S3Fifo/ClockPro/LruK-warm). Every access does:

  - `_rc[s]++`, re-band, and MOVE the block to the MRU of its band: 0 link writes when it is already
    the band MRU of its UNCHANGED band, else AT MOST 5 (4..5: a <= 2-write detach + a <= 3-write head
    push -- a tail-of-band re-band into its own band's head is 4, an interior detach + non-empty
    head push is 5). Real list surgery, said plainly in the code comment, README and llms.txt.
  - a FIXED m-1 = 7-step aging sweep: for each band Q1..Q7 (ascending) demote its tail IF expired,
    at most 4 link writes each (a <= 1-write TAIL detach + a <= 3-write head push into the band
    below). Worst case 7 x 4 = 28.
  - exactly 3 metadata stamps on the accessed slot (`_rc`, `_qn`, `_exq`); each aging demotion adds
    2 more (`_qn`, `_exq` on the demoted slot).

So the per-access LINK total is <= 5 + 28 = 33, and this 33 is a GENUINE, NON-EXCEEDABLE ceiling,
not a false constant. The key argument is RESET-ON-DEMOTE FORBIDS CASCADE: the sweep visits each
band Q1..Q7 exactly once, ascending; a demoted block lands at the HEAD of the band BELOW (already
visited this sweep) with a FRESH `_exq = _t + lifeTime` (not expired), so it is NEVER re-examined or
re-demoted within the same access. Therefore at most one demotion per band, at most 7 demotions, at
most 28 aging link writes -- a real constant. This was verified three ways: (1) walking the sweep by
hand (above); (2) `CountedMq` in t6 measures the worst-observed links/access over a mixed churn AND
an adversarial band-decay stream and asserts it never exceeds 33 (worst-OBSERVED ~17, because in
practice idle blocks decay gradually, one band per lifeTime window, rather than all 7 bands
expiring in the same access); (3) `CoveredMq` asserts max-demotions-per-sweep <= 7 (no cascade
slipped the guard). The 33 is pinned like Lfu's proven <= 14, NOT tripwired like ClockPro's honest
O(capacity) worst case. If a future change let a block cascade, (3) fails LOUD.

The measured worst-observed per-access cost (t6 Gate MQ, capacity 4096): max links/access = 17,
max stamps/access = 12, max demotions/sweep = 3 -- all well within the proven 33-link / (3 +
2*demotions)-stamp ceiling.

### D27.7 -- snapshot captures the queues, the columns, the clock and the Qout+refcounts

`dump()` captures the 8 band queues (values/expiry via the shared `snapList`), their aligned `_rc`
+ `_exq` columns, the logical clock `_t` (as `tick`, since `snapBase` owns `t` = capture time), and
the bounded Qout (keys as `hist` + aligned refcounts as `histRc`). Dropping the refcounts, the
expire times, the clock or the Qout is a fail-OPEN future-eviction bug, so all are captured and
`restore()` fails CLOSED on: any tag/shape mismatch; a malformed/mis-aligned rc or exq column; a
non-finite rc/exq; a `tick` that is not a non-negative finite number; and a history/histRc length
mismatch or over-bound history. The t9 controls (`mq-no-aging` differential, `mq-drop-rc`
round-trip) prove the policy and the round-trip have teeth.

## Consequences

- A new named export `Mq` + `MqHistory` (internal) in `Lru.js`; an `Mq` type in `Lru.d.ts`; a
  `makeMqOracle` differential oracle; harness wiring (`wrapMq`, `mqPolicy`/`mqIntPolicy`/
  `mqTtlPolicy`, `CountedMq`, `MQ_WRITES_*`/`MQ_STAMPS_ACCESS`, `SNAP_MEMBERS`); t0/t2/t5/t6/t7/t9
  coverage; validate term 16; the perf gate (24 scenarios), the bench roster and the demo counts;
  README + llms.txt roster/API/counts.
- The family is now twelve members under one surface. The zero-GC laws hold: the hot path is
  zero-alloc, the `_rc`/`_exq`/`_qn` columns + the 8 queue head/tail arrays are preallocated with
  the store, and the Qout + its refcount ring are fixed-size. The one HONEST caveat is that an MQ
  hit does real list surgery (0, or at most 5 (4..5), link writes) plus the fixed 7-step aging sweep -- said plainly
  everywhere, with a PROVEN <= 33-link / 3-stamp-plus-2-per-demotion per-access ceiling, never a
  false zero-write claim.
