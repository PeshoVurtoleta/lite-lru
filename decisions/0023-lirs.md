# 0023 -- LIRS: the eighth member, a bounded non-resident history, D23

Status: accepted (S16 -- the scan/loop-resistant stretch member; eviction by recency-of-recency)

## Context

S16 adds LIRS (Jiang & Zhang, SIGMETRICS'02 -- "Low Inter-reference Recency Set") as
the eighth `LiteCache<K,V>` family member. LIRS evicts by RECENCY-OF-RECENCY: a
block's IRR (inter-reference recency) is the count of DISTINCT blocks referenced
between its last two accesses. Low-IRR blocks (the LIR set) are hot and stay resident;
high-IRR blocks (HIR) are cold -- resident in a small reserve, or non-resident
metadata only. It is the strongest scan/loop resistance in the family and a genuinely
NEW mechanism vs recency (LiteLru), lazy-promotion FIFO (Sieve/S3Fifo), frequency
admission (WTinyLfu), segmented recency (Slru/TwoQ), or adaptation (Arc).

It rides the SAME `SlotStore` substrate (decisions/0011) via the shared `newStore`
factory: default Map backing, opt-in `keys:'int'` strict-zero backing, the same
`[lite-lru]`-tagged int-key door, the conservation invariant, the onEvict fire-after
+ `_inOnEvict` reentrancy guard (decisions/0002), TTL (decisions/0017), zero-GC
iteration (decisions/0018), opt-in stats (decisions/0019), and snapshot/restore
(decisions/0021). No new file; `Lirs` is a named export in `Lru.js`.

Textbook LIRS keeps a STACK S that mixes LIR blocks, resident-HIR blocks AND
non-resident-HIR blocks (metadata for evicted blocks) in recency order, with only a
loose practical bound on the non-resident portion, plus a list Q of resident-HIR
blocks (the eviction candidates). Suite law 3 requires ALL auxiliary metadata bounded
at construction -- so the non-resident history MUST be bounded. This decision owns
that tension up front.

## The decision -- D23

### D23.1 -- ONE `Lirs` named export, no sibling, no mode flag

A single `Lirs` named export over the shared substrate (the file-shape ruling shared
with every member: single main file + `sideEffects:false` + named exports -- the
tree-shake moat). Each hot path stays monomorphic. No new file.

### D23.2 -- the resident split; fixed-capacity honesty (restates Arc's D16.2)

The RESIDENT value capacity is EXACTLY `capacity`. It is split into
`L_hir = max(1, round(capacity * 0.01))` resident-HIR slots and
`L_lir = capacity - L_hir` LIR slots. Only the split is fixed; the total never moves.
`|LIR| + |resident HIR| == size` always (a conservation term in `validate()`).

Degenerate edges construct and behave: `capacity 1 -> L_hir 1, L_lir 0` (the all-HIR
window edge -- no LIR blocks ever exist, so the promotion path is guarded by
`L_lir > 0` and the cache behaves FIFO-like over Q). caps 1..4 are pinned in
`test/Lirs.test.js` and the t5 corpus.

### D23.3 -- the bounded non-resident history is a keys-only RING (generalizing ArcGhost)

The rejected alternative is textbook LIRS's UNBOUNDED stack S (its non-resident
portion grows with the trace). REJECTED under law 3.

Instead, the non-resident HIR history is a SEPARATE, bounded, keys-only ring --
`class LirsHistory extends ArcGhost` -- sized to `capacity`, strict zero-alloc on
`keys:'int'` (open-addressed int ring + membership table) and amortized on the Map
backing (Set + FIFO array). It stands in for the non-resident portion of the stack:
a non-resident HIR block is "still in S" iff its key is still in this ring. When the
bound is hit we drop the OLDEST key (FIFO). A resident HIR that is evicted from Q's
front records its key here ONLY if it was in the stack S at eviction (matching
textbook LIRS, where a resident-HIR not in S is simply forgotten on eviction). A
history hit re-admits the block as LIR (removing it from the ring) -- the
loop/scan discriminator.

This is a bounded, honest DEVIATION from unbounded LIRS: membership in the ring is
FIFO-recency-of-eviction, not stack-position relative to the bottom LIR. It is a
distinct, self-consistent bounded-LIRS variant; the differential oracle
(`test/torture/oracles/lirs.mjs`) implements the SAME bounded semantics, so the
member and the oracle agree exactly over the T5 corpus (both backings, +/- ttl).

### D23.4 -- the on-slot structure; the `_st` byte; the hot-path test

The stack S rides its OWN member link columns `_sNext`/`_sPrev` (a resident block can
be in BOTH the shared list AND S, so S needs separate links). The shared `_next`/
`_prev` thread a DISJOINT resident partition -- the LIR list (`_lirHead`/`_lirTail`)
and the list Q (`_qHead`/`_qTail`) -- so `validate()`'s conservation sum and the
shared zero-GC `CacheIterator` reuse the shared machinery unchanged (iteration order:
the LIR list then Q, resident-only, non-resident history excluded).

Per-slot state is a member-specific `_st` Uint8 column (like WTinyLfu's sketch -- NOT
a field on the shared `SlotStore`, so the OTHER seven members' hot paths stay
byte-identical): `bit0 = LIR`, `bit1 = inS`. The whole LIRS hot test is a single
`_st[s]` read. A LIR hit at the TOP of S early-returns with 0 link writes (pinned like
LiteLru's head re-hit 0/5/4); a LIR hit elsewhere is the 5-write "move to top of S".
The resident-HIR-hit reclassification and the miss/replace path reach the cold,
allocation-free helpers `_prune` / `_promoteToLir` / `_demoteBottomLir` / `_replace`
-- NEVER inlined into the LIR-hit body.

### D23.5 -- the pruning characteristic: MEASURED, never capped (owner ruling)

STACK PRUNING drops HIR blocks from the bottom of S until the bottom is a LIR. The
owner ruling: do NOT silently cap pruning (that breaks LIRS correctness); MEASURE it.

A consequence of D23.3 (the ring realization): because the non-resident history is a
SEPARATE ring and is NOT threaded into the linked stack S, the stack S holds ONLY
resident blocks (LIR + resident HIR). The number of resident HIR is bounded by
`L_hir`, so a single access's prune walks AT MOST `L_hir` entries -- `O(L_hir)`, i.e.
`O(0.01 * capacity)`, NOT the `O(capacity)` worst case of textbook LIRS (where
non-resident metadata accumulates IN the stack). This is a structural property of the
chosen ring design, not a cap on correctness.

MEASURED at capacity 4096 under the ADVERSARIAL max-pruning trace (stack the whole
resident-HIR reserve at the bottom of S above a single deep LIR, then touch that LIR
so the move-to-top prunes the entire run in one access -- `test/torture/t2` and the
`t6 Gate LIRS` report): max prune length = 41 (== `L_hir` for cap 4096), worst-case
single op ~0.02 ms, gate `maxPauseMs` 0.000, well under the 4 ms budget. The pause
budget is never at risk; the latency is documented honestly here rather than hidden.

### D23.6 -- the counting law, iteration order, snapshot aux (cross-cutting joins)

- Stats (D19.2, outcome-based): `get` drives hits/misses; `has`/`peek` are neutral;
  `put` drives puts + one eviction at the real victim (Q front). A `get` on a key that
  is only in the non-resident history is a plain MISS (reclassification to LIR happens
  only on a `put` that re-admits the key) -- pinned in `test/Lirs.test.js`.
- Iteration (D18): the LIR list then Q, RESIDENT only, non-resident history EXCLUDED;
  zero-GC, recency-neutral, stale-skipping, fail-closed via `_ver`.
- Snapshot (D21): `dump()` captures the LIR list + Q (values, + expiry when ttl on),
  the per-Q inS bits, the stack S order (slot indices top..bottom), and the bounded
  history VERBATIM (keys only). `restore()` reconstructs the SAME slot layout, links,
  per-slot `_st`, and history, so a restored cache makes IDENTICAL future eviction
  decisions vs an un-snapshotted twin. Fail-closed restore: tag `{ f:'litelru/1',
  m:'Lirs', ... }` + a rejection matrix (malformed inS/stack/history columns, a stack
  slot that is not a resident LIR/inS-HIR, a history over its bound) -- pinned by
  `test/Lirs.test.js`'s restore fail-closed matrix (this is what actually proves a
  dropped/malformed snapshot column is rejected, not the t9 controls below). The two
  t9 controls (`lirs-drop-ins-bit`, `lirs-no-history`) are a SEPARATE proof: they pin
  LIVE-POLICY divergence vs the differential oracle -- a `Lirs` subclass whose ACCESS
  POLICY ignores the inS bit, or whose non-resident history is a no-op, drifts from the
  bounded-LIRS oracle's LIR set / next-eviction victim over a fuzzed trace (D23.3's
  mechanism actually matters at runtime, not just at snapshot time), independent of
  snapshot serialization entirely.

## Consequences

- The bounded-ring history is a documented deviation from unbounded LIRS; the loop/
  scan resistance (the reason to ship LIRS) is preserved -- measured on the in-repo
  bench: loop 24.7% hit (99.2% of Belady OPT, where LRU/Sieve/S3Fifo are ~0), scan
  100% of OPT, zipf 87.1% of OPT (cap 256, 200k ops).
- Pruning is `O(L_hir)` not `O(capacity)` -- a strict latency improvement over
  textbook LIRS, at the cost of the deviation in D23.3. Measured + pinned, never
  capped.
- Every hot path (LIR hit / resident-HIR hit / miss-replace) is strict zero-alloc
  (t6 Gate LIRS: 0.00000 B/op at capacity 4096; the stack/Q/LIR-list/`_st`/int-index/
  history-ring backings never grow). The other seven members' `get`/`put` bodies are
  byte-identical (Lru.js diff is purely additive Lirs code).
