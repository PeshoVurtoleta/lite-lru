# 0024 -- Lfu: the ninth member, an O(1) EXACT LFU, D24

Status: accepted (S17 -- the exact-frequency member; eviction by exact access count with an LRU tie-break)

## Context

S17 adds `Lfu` as the ninth `LiteCache<K,V>` family member: an EXACT Least-Frequently-Used
cache. It evicts the key with the LOWEST exact access frequency; within a frequency it breaks
the tie by recency (LRU). This is the EXACT counterpart to the approximate-sketch `WTinyLfu`
(decisions/0014): where WTinyLfu ESTIMATES frequency with a saturating count-min sketch (fast,
sub-linear memory, but probabilistic), `Lfu` counts EXACTLY and guarantees "the least-
frequently-used resident is the victim" -- a provable property, not a statistical one.

It rides the SAME `SlotStore` substrate (decisions/0011) via the shared `newStore` factory:
default Map backing, opt-in `keys:'int'` strict-zero backing, the same `[lite-lru]`-tagged
int-key door, the conservation invariant, the onEvict fire-after + `_inOnEvict` reentrancy
guard (decisions/0002), TTL (decisions/0017), zero-GC iteration (decisions/0018), opt-in stats
(decisions/0019) and snapshot/restore (decisions/0021). No new file; `Lfu` is a named export in
`Lru.js`.

The naive exact-LFU is a priority queue -> O(log n) per access. The whole family is O(1) on the
hot path, so an O(log n) member would be a regression. This decision owns the structure that
keeps it O(1).

## The decision -- D24

### D24.1 -- ONE `Lfu` named export, no sibling, no mode flag

A single `Lfu` named export over the shared substrate (the file-shape ruling shared with every
member: single main file + `sideEffects:false` + named exports -- the tree-shake moat). Each
hot path stays monomorphic. No new file.

### D24.2 -- structure: the Shah-Matani O(1) LFU (a list OF frequency buckets)

The structure is a doubly-linked list OF frequency BUCKETS in ascending frequency order
(`_bMin` = head = the LOWEST frequency = the eviction end). Each bucket owns a recency list of
resident key-slots at ONE exact frequency; the frequency lives ON the bucket (`_bFreq`), shared
by every key in it. This is the classic Shah-Matani "constant-time LFU" (Prashanth Shah,
Ketan Matani, 2010): all four of get/put/increment/evict are O(1) -- NOT O(log n).

  - increment (a hit): read the key's bucket `b` (freq f); find or create the bucket at freq
    f+1 (it is `b`'s successor in the list, or a freshly-allocated bucket inserted right after
    `b`); move the key there; if `b` is now empty, unlink + free it. O(1).
  - evict: take the LRU-end key of `_bMin`. O(1).

### D24.3 -- within-bucket tie-break = LRU

Each bucket's key list is a RECENCY list (`_bHead` = MRU, `_bTail` = LRU). A newcomer (freq 1)
and a just-promoted key attach at the MRU end; eviction removes the LRU-end key of the lowest-
frequency bucket. So `Lfu` is LFU-with-LRU-tiebreak: among equally-cold keys, the least-recently-
used is the victim -- the intuitive and testable choice, and the one the brute oracle mirrors.

### D24.4 -- the frequency column is a Float64Array (exact to 2^53), NOT Int32

Frequencies are stored per BUCKET in a `Float64Array` (`_bFreq`), exact to 2^53. This restates
the stats D19.4 rationale: an Int32 counter wraps at 2^31 (~2.1e9), which a long-lived hot key
reaches; a Float64 integer is exact to 9.0e15. A wrapped frequency would silently mis-order
eviction -- a fail-OPEN bug. Float64 is the honest, exact choice.

### D24.5 -- the bucket POOL is preallocated and fail-closed, never `new` per bucket

There are at most `capacity` distinct frequencies among <= capacity keys (every live bucket
holds >= 1 key), so `capacity` bucket nodes are provably sufficient. The pool is a fixed set of
`capacity` nodes (`_bFreq` Float64Array + `_bNext`/`_bPrev`/`_bHead`/`_bTail` Int32Array) drawn
from a `_bFree` stack. A bucket is NEVER allocated with `new` on a hot path. Exhaustion is
provably unreachable in a coherent cache; if it ever fires an invariant broke, so we fail CLOSED
(`LFU_POOL_MSG`) rather than grow.

The bucket pool is zero-alloc under frequency churn: the t6 Gate LFU tier asserts every `_b*`,
`_f*` and `_kB` byteLength is invariant across a 60k-op window and that live + free buckets ==
capacity always. Members' resident keys ride the dedicated `_fNext`/`_fPrev` columns (with `_kB`
the owning-bucket tag), keeping the shared `_next`/`_prev` free for the store's slot free stack.

### D24.6 -- the single-key relabel fast path

If a hit falls on the ONLY key in a bucket and there is no freq+1 neighbour, the bucket is
RELABELLED in place (`_bFreq[b]++`) -- the key stays put, no bucket is created or destroyed.
This keeps a single hot key at 1 write/hit (the pinned fast path) instead of a create+destroy
churn, and keeps the bucket pool from thrashing. Ascending order is preserved (the predecessor's
freq < target, and the successor -- if any -- has freq != target and > the old freq, hence
> target).

### D24.7 -- a hit is zero-ALLOCATION but NOT zero-write (DEBATE-honest)

A hit relinks a key across frequency buckets: it is zero-ALLOCATION (all nodes come from the
preallocated pool) but NOT zero-write. The honest pitch is exactly that. The t6 Gate LFU tier
measures and PINS the writes-per-hit: the fast-path relabel is 1 write; the worst-case relink
(create the freq+1 bucket + move the key while the source bucket keeps other keys) is bounded at
14 index stores. This is the DEBATE item-2 discipline (measure the writes; never claim
"lock-free" or "zero-write"), applied to LFU.

### D24.8 -- put-update counts as a hit; has/peek are frequency-neutral

`put(k, v)` on a resident key rewrites the value AND increments the frequency (an update IS an
access). `has()` and `peek()` are inspections, not accesses -- they never change frequency,
matching every other member's recency/promotion neutrality.

### D24.9 -- snapshot captures EXACT frequencies verbatim (dropping them is fail-OPEN)

`dump()` captures the buckets in ascending order, each with its EXACT `freq` and its full within-
bucket key ordering (MRU..LRU). `restore()` reconstructs the exact frequencies and ordering, so a
restored cache makes IDENTICAL future eviction decisions vs an un-snapshotted twin fed the same
trace (D21.1). Dropping the frequency data -- defaulting it, or compacting away the gaps between
counted frequencies -- is a fail-OPEN bug: future promotions merge buckets after the WRONG number
of accesses, so the victim drifts. The t9 `lfu-freq-dropped` control proves the round-trip
differential catches exactly that. `restore()` fails closed on a non-array `buckets`, a
bad/absent/non-ascending frequency, an empty bucket, a duplicate/out-of-range slot, and residents
> capacity (REJECT, never truncate).

## The DEBATE rebuttal

  - "exact LFU is O(log n) -- the wrong tool for a zero-GC hot path." REBUTTED. The Shah-Matani
    list-of-buckets (D24.2) is O(1) for get/put/increment/evict -- not O(log n). There is no heap,
    no comparison, no sift. The docs previously disclaimed "exact LFU is the wrong tool"; that line
    now points AT `Lfu`, and the gap it named is closed.
  - "a frequency cache should just use the WTinyLfu sketch." REBUTTED. The sketch is APPROXIMATE
    (saturating count-min): it trades exactness for sub-linear memory and is the right default for
    admission control. But when you need a PROVABLE "the least-frequently-used key is the victim"
    -- audits, quota fairness, deterministic replay -- an estimate is not enough. `Lfu` is exact.
    The t9 `lfu-approx-freq` control (a saturating-at-2 counter) proves a coarse approximation
    diverges from the exact-LFU oracle -- i.e. that the exactness is load-bearing, not decorative.
  - "a hit does no work, like SIEVE." REBUTTED (honesty). A `Lfu` hit relinks a bucket -- zero-
    ALLOCATION but NOT zero-write (D24.7), pinned at <= 14 writes/hit. We state this plainly rather
    than overclaim.

## Consequences

  - The ninth member; the family now spans recency (LiteLru), lazy-promotion FIFO (Sieve/S3Fifo),
    APPROXIMATE frequency admission (WTinyLfu), EXACT frequency (Lfu), segmented recency
    (Slru/TwoQ), adaptation (Arc), and recency-of-recency (Lirs) -- one `LiteCache<K,V>` surface,
    one-line policy swap.
  - New per-slot columns `_fNext`/`_fPrev`/`_kB` and the bucket pool `_bFreq`/`_bNext`/`_bPrev`/
    `_bHead`/`_bTail` + `_bFree`/`_bMin`; all fixed-size, allocated once, never grown. The other
    members' hot paths are byte-identical (no field added to the shared `SlotStore`).
  - A new conservation term in `validate()` (the bucket list is coherent + strictly ascending, the
    pool is conserved, `_kB` agrees, the columns never grow); a new brute oracle
    (`test/torture/oracles/lfu.mjs`, exact freq map + LRU tie-break, sharing no code with the SoA
    member); harness `lfuPolicy`/`lfuIntPolicy`/`lfuTtlPolicy`; `Lfu` added to t0/t2/t5/t6/t7 and to
    the snapshot round-trip roster; two t9 must-fail controls (`lfu-approx-freq`, `lfu-freq-dropped`);
    a boundary suite (`test/Lfu.test.js`); the bench MEMBERS + the demo renderer + roster.
