# 0017 -- TTL: the opt-in, lazy, zero-GC expiry column, D17

Status: accepted (S10 -- the opt-in TTL feature, all four members)

## Context

S10 adds an OPT-IN time-to-live to the whole family (`LiteLru`, `Sieve`, `S3Fifo`,
`WTinyLfu`) under the SAME `LiteCache<K,V>` surface. The design constraints are the
suite's, not a convenience wrapper's:

  - Zero allocation on EVERY hot path for ALL FOUR members, ttl on OR off.
  - PAY-FOR-WHAT-YOU-USE: a cache that never asks for ttl must be byte-identical to
    the pre-TTL build -- no extra column, no per-op check that costs writes.
  - Fail closed: a bad `ttl` / `ttlMs` / `clock`, or a per-put `ttlMs` on a cache with
    no ttl configured, throws a `[lite-lru]`-tagged error at the door. null is not zero.
  - LAZY, no timers: this is a zero-GC data structure, not a scheduler. Nothing runs in
    the background; nothing is async. Expiry is observed on the next touch.

TTL is a column on the shared `SlotStore` substrate (decisions/0011), threaded through
the shared `newStore` factory and reused by every member -- the same composition move
Sieve/S3Fifo/WTinyLfu already make. It reuses the onEvict fire-after + `_inOnEvict`
reentrancy guard (decisions/0002) verbatim for every reap.

## The decision -- D17

### D17.1 -- `_exp` is a nullable Float64Array of ms timestamps, allocated on ttl only

The expiry column `_exp` is one `Float64Array` slot per cache slot (8 bytes each),
holding an absolute ms timestamp: `expiresAt = now() + ttlMs`. Never-expire is
`Infinity`, NEVER `0` (a Float64Array defaults to 0, which would read as "expired at
time 0" -- fail-open; so the column is `.fill(Infinity)` at construction and a freed
slot is reset to `Infinity`). It is allocated ONLY when a `ttl` option is supplied;
otherwise `_exp === null` and the ttl-OFF hot path never touches it. `_exp` lives on
`SlotStore` (ctor/`freeSlot`/`reset`), is threaded through `newStore`, and is cached on
each policy as `this._exp` for direct hot-path access -- exactly like `_keys`/`_vals`.
`validate()` gains a conservation term: `_exp.length === capacity`, its buffer is the
fixed construction size (never grown), and every FREE slot reads `Infinity` (the
retention-hygiene mirror of the payload columns).

### D17.2 -- the clock is `Date.now` by default, injectable and validated

`get`/`put`/`has`/`peek`/`purgeStale` read the current time through `this._clock()`,
`Date.now` by default. An injectable `clock` option (a hoisted zero-arg function
returning ms) makes the whole feature deterministically testable -- the torture
differential drives a VIRTUAL clock shared by the real cache and its oracle, so lazy
expiry is fuzzed in lockstep. `clock` is validated function-or-undefined at the door;
anything else throws a `[lite-lru]` TypeError (fail closed). Keep it a hoisted function,
not a per-call closure (zero-GC).

### D17.3 -- LAZY, check-before-policy: stale = MISS, reaped in place, no promotion

The staleness gate fires in `get`/`has`/`peek` BEFORE the member's hit policy runs. A
stale entry is a MISS: no LRU promotion, no SIEVE/S3-FIFO visited bump, no W-TinyLFU
sketch bump or segment relink. It is REAPED in place (the member's delete body + fire
onEvict via the 0002 guard) and the call returns `undefined`/`false`. Two consequences
are load-bearing and the oracles mirror them EXACTLY (else the T5 differential diverges
falsely):

  - Capacity eviction does NOT prefer stale slots. An untouched stale entry still counts
    toward `size` and is evicted by the ordinary policy victim, not preferentially -- it
    is only reaped when a touch (`get`/`has`/`peek`) or `purgeStale()` reaches it.
  - `has`/`peek` are read methods with NO reentrancy throw (decisions/0002), yet a stale
    touch now mutates (reaps). To stay fail-closed they skip the physical reap when
    `_inOnEvict` is set (never nest an onEvict), still reporting the stale entry as a
    miss. Outside a callback they reap normally.

### D17.4 -- per-instance `ttl` default + positional `put(key, value, ttlMs?)`

A cache gets a ttl DEFAULT from the `ttl` option; an individual entry overrides it with
a positional `ttlMs` on `put`: a positive finite number of ms, `Infinity` for never, or
omitted for the default. Positional (not an options object) so the hot `put` stays a
plain call with no per-op object allocation. Fail-closed rules:

  - `ttlMs` on a cache with NO ttl configured throws a `[lite-lru]` Error (there is no
    `_exp` column to stamp -- a caller bug, not a silent no-op).
  - `ttl` (default) and `ttlMs` (per-put) must be positive-finite-or-Infinity; `<= 0`,
    `NaN`, and non-numbers throw a `[lite-lru]` RangeError.

### D17.5 -- `purgeStale()`: cold, O(size), evict-every-expired

`purgeStale()` is the explicit, COLD reclamation path (never a hot path): it walks the
keyed index once, reaps every currently-expired resident (firing onEvict per victim via
the 0002 fire-after + reentrancy guard), and returns the count. Because it is cold it
MAY allocate a small victim list; it is uniform across all four members (it reuses each
member's `_reap`). Returns `0` on a cache with no ttl.

Reentrancy during a purge is fail-closed, NOT a completion guarantee. A well-behaved
onEvict (the 0002 contract: no put/get/delete/clear/purgeStale on the same instance)
lets the sweep reap every stale resident. If an onEvict VIOLATES that contract mid-sweep,
the guard throws and the throw propagates straight out of `purgeStale()` -- the sweep
stops, and stale residents ordered after the offender are left resident (still indexed,
still counted). This is intentional: papering over a contract violation to keep reaping
would be fail-OPEN. The cache stays STRUCTURALLY consistent (conservation holds for
whatever was reaped before the throw -- `validate()` passes), and because TTL is lazy the
un-reaped stales are ordinary stale entries: the next get/peek/has that touches one, or a
subsequent `purgeStale()`, reaps it. So `purgeStale()` guarantees "structurally
consistent, and stale-free UNLESS an onEvict threw" -- never a partial-corruption state.
Pinned as a regression guard in `test/Ttl.test.js` (section H) across all four members and
all five reentrant ops.

### The off-path decision, RESOLVED BY MEASUREMENT: (a) a single monomorphic guard

The one open question was how to keep the ttl-OFF hot path byte-identical. Two options:
(a) a single monomorphic `this._exp === null` guard on each hot method, kept iff T6
shows no regression; (b) constructor-time method specialization if (a) regressed.

MEASURED (T6, this build): option (a) holds -- KEPT.

  - ttl-OFF writes-per-hit are UNCHANGED from the S1 baseline: head/interior/tail =
    0 / 5 / 4 (CountedLru). The `this._exp === null` branch is predicted-not-taken and
    writes nothing; a non-ttl cache has `_exp === null` (no column allocated).
  - ttl-ON is STRICT zero-alloc: an int-backed ttl cache churning fresh keys (put stamps
    `_exp`, an older stale get reaps in place) under a virtual clock measures
    `gc major=0 minor=0 maxMs=0.00`, `alloc=0.00032 B/op` (< 1 B/op), and
    `_exp.byteLength` is stable start-to-finish (32768 = capacity * 8), alongside
    `_next`/`_prev`/the int index buffers.

So no constructor-time specialization is needed; one guard per hot method is free on the
off path and zero-alloc on the on path. Recorded here so (b) is a decision not taken,
not an oversight.

### Uniform surface + policy law unchanged

TTL is additive to the `LiteCache<K,V>` surface: `put` gains an optional trailing
`ttlMs`, and `purgeStale(): number` joins the surface (all four members implement it).
`new LiteLru(n, { ttl })` still swaps for `new Sieve(n, { ttl })` etc. and stays
type-checked. The D7 undefined-value contract holds -- a stale entry storing `undefined`
becomes a genuine miss for get/has/peek alike. The onEvict reentrancy contract (0002)
holds for every reap.

## Consequences

  - One fixed structure is added ONLY when `ttl` is configured: `_exp` (8 bytes/slot),
    allocated once, never grown; `byteLength` invariant under churn (t6 Gate TTL-ON and
    `validate()` assert it). A non-ttl cache adds nothing (`_exp === null`).
  - `freeSlot`/`reset` drop the expiry (`Infinity`) so a reused slot can never inherit a
    stale timestamp; `clear` resets the whole column. The t7 census proves expired /
    evicted / cleared VALUE objects are collectible -- `_exp` holds primitive timestamps
    only, it pins nothing.
  - Lazy TTL is a NAMED, gated law: t0 (stale = miss + no promotion, per-put override,
    Infinity never, capacity-eviction-does-not-prefer-stale), t1 (fail-closed throws +
    D7 under ttl), t2 (the get/has/peek lazy triple across all four members), t5 (the
    virtual-clock differential vs each oracle -- value + size + victim), t7 (expiry churn
    + conservation + purgeStale + value census). t9 controls C-skip-gate,
    C-stale-promotes and C-growing-_exp each prove the gate REJECTS a broken ttl policy.
  - The public API is additive; VERSION stays "1.2.0" (moves only at /release).
